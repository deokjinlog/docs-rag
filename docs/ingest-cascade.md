# 인제스트 캐스케이드 — 적응형 라우팅 설계

**목표**: "더 잘 읽는다"가 아니라 **어떤 PDF 가 들어와도 안 깨지고, 비싼 경로는 필요한
페이지에만 쓴다.** 지금은 모든 PDF 를 ODL 한 경로로 보내는데, 네이티브 PDF 뿐이라 맞지만
스캔본 특약이나 팩스 이미지가 들어오면 **조용히 빈 텍스트**가 나온다.

## 티어

```
Tier 0  NATIVE          텍스트 레이어 정상          → ODL + bbox 재구성   (지금 것)
Tier 1  NATIVE_SUSPECT  레이어는 있으나 깨짐        → OCR 재추출 후 비교
Tier 1  SCAN_SIMPLE     텍스트 없음 · 단순 레이아웃  → PP-StructureV3 (OCR)
Tier 2  SCAN_COMPLEX    텍스트 없음 · 표/다단/회전   → PaddleOCR-VL
```

**"OCR vs VL" 이 아니라 "네이티브 vs OCR vs VL"** 이다. VL 은 OCR 의 대체가 아니라
OCR 이 못 푸는 페이지의 마지막 폴백이다. 실측이 이걸 뒷받침한다 —
같은 이미지에서 [OCR 이 이긴 것](parser-vl-eval.md)과 VL 이 이긴 것이 갈렸다.

## M1 실측 (2026-09-08, data/input 3개 KB 약관 1,663페이지)

| 판정 | 페이지 | 비중 | 경로 |
|---|---|---|---|
| NATIVE | 1,575 | **94.7%** | ODL |
| NATIVE_SUSPECT | 0 | 0.0% | — |
| SCAN_SIMPLE | 20 | 1.2% | OCR |
| SCAN_COMPLEX | 68 | 4.1% | VL |

### 임계치가 데이터로 검증됐다

감으로 정한 값이 실제 분포에서 두 무리 사이에 정확히 앉았다:

```
NATIVE        char_count min =  66   ┐  50~66 이 비어 있다
                                     ├→ 임계 50 이 정확히 그 사이
SCAN_COMPLEX  char_count max =  46   ┘
SCAN_SIMPLE   char_count max =  28

image_cover   max = 0.756  < 임계 0.80  → 진짜 스캔 페이지 0개
garbage_ratio max = 0.012  < 임계 0.15  → 깨진 텍스트 레이어 0개 (임계의 1/12)
```

`garbage_ratio` 가 0 이라는 건 한글 CID 폰트 문제가 이 코퍼스엔 없다는 뜻이다.
다른 회사 약관이 들어오면 달라질 수 있어 신호는 남겨둔다.

### 예산 — 이 설계의 값어치

```
전량 VL      1,663p × 72.5s = 33.5시간
캐스케이드      68p × 11s    = 12.5분     ← 160배 절감
```

## 설계 원칙

**분류를 LLM/VLM 에 맡기지 않는다.** 98% 정확도 분류기도 1,000건이면 20건을 엉뚱한 경로로
보낸다. 규칙은 틀리는 방식이 예측 가능해 디버깅이 되고 페이지당 수 ms 로 끝난다.
이 프로젝트의 precision-first 와 같은 규율이다.

**깨진 레이어를 먼저 본다.** `classify()` 가 `garbage_ratio` 를 `char_count` 보다 **먼저**
검사하는 이유 — char_count 로 먼저 통과시키면 깨진 텍스트가 NATIVE 로 새어 조용히
쓰레기를 색인한다. 한글 PDF 의 흔한 실패는 "텍스트가 없다"가 아니라 "있는데 깨졌다"다.

**혼합 페이지**(네이티브 텍스트 + 이미지 표)는 페이지 전체를 VL 로 보내지 않는다.
텍스트는 ODL 로, 이미지 영역만 crop 해서 VL 에 넣고 bbox 위치에 끼운다.
공통 스키마가 block 단위라 가능해진다(M2).

## M3 실측 — 합성 스캔셋으로 OCR vs VL (2026-09-08)

네이티브 PDF 를 래스터라이즈해 **정답이 딸린** 스캔셋을 만들었다(본문 6페이지 × 변형 4 = 24장).
정답은 텍스트 레이어. 어제 "골든 원본 PDF 가 없어 회귀를 못 돌린" 지점을 이걸로 풀었다.

### 지표를 셋 두는 이유 — 앞의 둘이 서로 반대로 편향돼 있다

| 지표 | 무엇을 보나 | 편향 |
|---|---|---|
| **3-gram 겹침** | 글자를 맞게 읽었나 (순서·줄구조 무관) | **없음 → 판정 기준** |
| 줄 recall | 정답 줄이 예측에 있나 | 줄 단위로 뱉는 **OCR 에 유리** |
| CER | 편집거리 (순서 포함) | 읽기순서를 지키는 **VL 에 유리** |

실측이 그 편향을 드러냈다 — 줄 recall 은 OCR 3배 우세(0.75 vs 0.24), CER 은 VL 3배
우세(0.28 vs 0.76). 같은 데이터에서 정반대 결론이 나온다. 3-gram 이 그걸 가른다.

### 결과 (3-gram 기준)

| 변형 | OCR | VL | 차 | OCR 초/장 | VL 초/장 | 배수 |
|---|---|---|---|---|---|---|
| clean (200dpi) | 0.691 | **0.867** | +0.176 | 4.0 | 94.7 | 24x |
| low (120dpi) | 0.672 | **0.883** | +0.211 | 1.9 | 62.6 | 33x |
| skew (2°) | 0.663 | **0.874** | +0.211 | 3.3 | 77.2 | 23x |
| dark (감마0.6) | 0.724 | **0.855** | +0.131 | 2.5 | 66.7 | 27x |

**VL 이 일관되게 우세하지만 20~33배 느리다.** 그리고 중요한 건 **열화에서도 격차가
안 벌어진다**는 것 — "깨끗하면 OCR, 열화되면 VL" 이 아니라 **"항상 VL 이 낫고 항상 비싸다"**.

→ **격상 조건을 열화 축에서 찾으면 안 된다.** M5 의 격상 신호는 이미지 품질이 아니라
  **내용 신호**여야 한다: OCR confidence(실측: 잘린 글자 0.117 vs 정상 0.95+), 표 존재,
  추출 문자 수 급감. 이건 triage 의 SCAN_COMPLEX 판정과 같은 축이다.

### 부수 발견 — 측정 설계에서 두 번 틀렸다

① **목차 페이지를 고르면 망가진다.** 글자 수만 보고 고르니 앞 6페이지가 전부 목차였고,
   정답의 상당 부분이 점선 리더였다. OCR 이 그걸 재현 안 하니 CER 0.81 — OCR 품질이
   아니라 페이지 선택 실패였다. → '제N조' 개수 + 점선 비율로 본문만 고른다.
② **좌표계가 다르면 재정렬이 깨진다.** OCR bbox 는 이미지 픽셀(200dpi 폭 ~1654),
   ODL 은 PDF 포인트(~595). 같은 COL_GAP(60)이면 픽셀 쪽에서 폭의 3.6% 라 2단 페이지에서
   경계가 **7개** 검출됐다. → `from_ocr(image_width=)` 로 A4 포인트에 정규화.

## M5 실측 — 격상 게이트의 전제가 틀렸다 (2026-09-08)

M3 은 변형별 **중앙값**만 봤다. 같은 24장을 **페이지별로** 분해하니 설계 전제가 무너졌다.

| | 범위 | 표준편차 |
|---|---|---|
| OCR 3-gram | 0.591 ~ 0.845 | **0.068** |
| VL 3-gram | 0.218 ~ 0.956 | **0.143** |

**OCR 은 균일하게 평범하다.** "OCR 이 실패한 페이지"라는 부분집합이 없다 —
그런 게 있어야 "여기만 VL 로 격상"이 성립하는데, 없다. 격상 트리거를 OCR 품질에서
찾으려던 계획은 잴 대상이 애초에 없었다.

**진짜 위험은 반대편에 있었다.** VL 이 한 장에서 완전히 무너졌다(0.218). 그것도
**가장 깨끗한 입력**에서 — 같은 페이지의 저해상도·기울기·과노출 변형은 0.80~0.90 으로
멀쩡했다. 이미지 품질과 무관한 실패다.

### 무너진 방식: 디코딩 루프

정답 1,331자짜리 페이지에 **4,556자**를 뱉었고, 8-gram 하나("00만원,500")가 **556번**
반복됐다. 자기회귀 생성의 전형적 폭주다. 처리 시간도 219.6초(정상 중앙 65초).

탐지 신호를 넷 재보고 두 개만 남겼다:

| 신호 | 정상 23장 최대 | 실패 1장 | 판정 |
|---|---|---|---|
| VL/OCR 글자수 비 | 3.70 | 3.98 | ❌ 안 갈림 |
| 처리 시간 | 103.6s | 219.6s | △ 갈리지만 하드웨어 종속 |
| **자기반복도**(1−고유 8-gram 비) | 0.252 | **0.955** | ✅ 3.8배 |
| **최다 8-gram 반복 횟수** | 8 | **556** | ✅ 70배 |

> **마크업을 먼저 벗겨야 한다.** VL 은 표를 HTML 로 뱉는데 `word-wrap: break-word` 가
> 셀마다 반복돼, 안 벗기면 멀쩡한 표 페이지의 자기반복이 0.646 까지 올라가 진짜 루프와
> 구분이 흐려진다. 벗기면 정상 최대가 0.252 로 내려앉는다.

### 그래서 게이트를 뒤집었다

```
계획:  OCR 품질이 나쁘면 → VL 로 격상          (트리거가 존재하지 않았다)
실제:  VL 을 썼으면 → 온전한지 보고, 아니면 OCR 로 되돌림
```

`scripts/vl_sanity.py` · 잠금 `tests/eval/test_vl_sanity.py` · 채점은 `make eval-scanset`
리포트 하단에 붙는다. 24장 실측 **정탐 1 · 오탐 0 · 미탐 0**:

```
평균  0.857 → 0.876       최악  0.218 → 0.693     ← 게이트가 사는 곳은 최악값이다
```

**임계는 비대칭이 정한다.** 오탐(멀쩡한 VL 을 버림)은 그 페이지가 OCR 품질(0.65)로
내려앉을 뿐이다. 미탐(루프를 통과시킴)은 "500만원"이 556번 박힌 청크를 색인해 **확신에 찬
오답**의 재료가 된다. 그래서 임계(자기반복 0.50 · 반복횟수 30)를 정상 최대에서 넉넉히 띄웠다.

> **한계 — 실패 표본이 1건이다.** 마진이 3.8배·70배라 칼날 위 임계는 아니지만, 다른
> 실패 모드(조용한 환각, 일부 누락)는 이 게이트가 못 잡는다. VL 을 실제 파이프라인에
> 태우면(M4) 표본이 늘고, 그때 임계를 재조정한다.

## 다음 단계

| # | 할 일 | GPU |
|---|---|---|
| **M1** | ✅ triage + 분포 리포트 (`make triage`) | 불필요 |
| M2 | 공통 스키마 — ODL/OCR/VL 출력을 `Block` 으로 통일, bbox 재구성이 Block 을 먹게 | 불필요 |
| M3 | 합성 스캔셋(네이티브 PDF 를 래스터라이즈) + CER 측정 → OCR 경로 기준선 | GPU |
| M4 | VL 폴백 + Celery `gpu` 큐(concurrency=1, 문서 단위 배치) | GPU |
| **M5** | ✅ 품질 게이트 — **VL 출력 온전성**(`vl_sanity`). 격상 트리거를 OCR 품질에서 찾으려던 계획은 실측으로 기각 | 불필요 |

M2 가 가장 값어치 있다 — **bbox 재구성이 읽기순서를 실제로 고치는 유일한 도구**인데
(ODL·하이브리드·VL 셋 다 실패, [실측](parser-vl-eval.md)), 지금은 ODL 출력에만 먹는다.
공통 스키마로 묶으면 OCR/VL 결과에도 그대로 적용된다.

**하지 말 것**: VL 전량 처리 · 분류를 LLM 에 맡기기 · 원본 PDF 없는 골든으로 회귀 판정 ·
분포 보기 전에 임계치 정하기 · **집계 중앙값만 보고 부분집합이 있다고 가정하기**(M5 가 이걸로 틀렸다).
