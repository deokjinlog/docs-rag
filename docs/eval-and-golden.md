# 평가·골든셋 방법론

추출·검색·답변의 **정확도를 측정하고 회귀를 막는** 체계. "완벽 파싱"이 아니라 **precision을
보증하고(틀린 건 안 냄) 나머지는 RAG가 받는** 우아한 열화가 원칙.

## 1. 핵심 원리 — 결정론은 검증, 확률적은 RAG

- **precision-first**: 못 뽑으면 **틀린 값 대신 NULL** → NULL은 RAG로 폴백. "확신에 찬 오답"을 0으로.
- **필요한 정확도 = recall이 아니라 precision.** recall(다 뽑기)은 불가능·불필요(RAG가 받음), precision(뽑은 건 맞기)은 원문 대조로 달성 가능.
- 근거: [The ML Test Score (Google, Breck et al. 2017)](https://research.google/pubs/pub46555/) — "모델이 아니라 데이터·전처리를 단계별로 테스트하라".

## 2. 두 도구 — 실패 로그(찾기) vs 골든셋(채점)

| | 실패 로그 | 골든셋 |
|---|---|---|
| 생성 | 코드 자동(NULL마다 이유 기록) | 사람이 정답 라벨 |
| 역할 | **어디가 구멍인지 찾기(진단)** | **고친 게 맞나 채점(검증)** |
| 측정 | NULL률(대략) | precision/recall(정확) |

서로 안 섞이는 별개 도구. 실패 로그로 "어디"를 찾고, 골든셋으로 "맞나"를 잰다.

## 3. 실패분석 루프 (4단계)

```
1. 실패 로깅   코드가 NULL을 (회사·포맷·이유)와 함께 기록
2. 군집화      로그 group-by → "반각 특약 담보명 26건 = 표참조형"  ← 무엇을 고칠지
3. 표본 진단   군집 3~5개 원문 열어 원인 파악 → 조치 방향
4. 타겟 수정   그 군집만 코드 고침 + 골든셋 재채점(순증?)          ← 언제 멈출지
```
- **군집화 = group-by**(SQL GROUP BY 같은 집계, ML 아님). 실패는 문서유형별로 뭉치니 하나 고치면 다수 해결.
- **정지 조건**: 목표 recall 도달, 또는 남은 군집이 꼬리(작음) → RAG로. 100% 안 쫓음(80/20).
- **왜 다 코딩 안 하나**: 꼬리는 무한·미지 + 규칙끼리 간섭(회귀) + RAG가 이미 받음 → 추가이득 0. 속도가 아니라 유지보수·회귀가 문제.

## 4. 골든셋 채점 — 필드 타입별 매칭

값(pred)과 정답(gold)을 **정규화 후 비교**. 생짜 ==(공백 하나로 fail)도, LIKE 포함(부분답 통과)도 아닌 중간:

| 필드 타입 | 매칭 | 예 |
|---|---|---|
| 코드·enum(계약유형·조번호·ICD) | 정확 일치 | "특약"=="특약" |
| 담보명·상품명 | **정규화 후 일치** | "중환자실 입원급여금"=="중환자실입원급여금" |
| 숫자(기간·지급률) | 단위 정규화 | "90일"=="90 일" |
| 자유서술(RAG 답변) | 토큰 F1 or LLM judge | "지급 안 됨"≈"지급되지 않습니다" |

- **정규화(`_norm`)** = NFKC + 공백제거 + 사소한 구두점 제거. [SQuAD `normalize_answer`](https://github.com/allenai/bi-att-flow/blob/master/squad/evaluate-v1.1.py)의 한국어판.
- **precision/recall/F1**: recall=안 빠뜨림, precision=뽑은 게 맞음, F1=2PR/(P+R) 조화평균.
- LLM judge 쓸 땐: 좁은 이진판정 + 근거 인용 + **judge를 메타-골든셋으로 검증** + 생성≠judge 모델.

## 5. 전처리 게이트 (단계별 검증)

최종 답 기다리지 말고 **각 단계 출력에 검사**를 박아 상류에서 차단:

| 단계 | 검사 | 잡는 것 |
|---|---|---|
| OCR | 한글 비율>50%, confidence | 깨짐 |
| 파싱 | **1..N 연속**, 조 개수(5~60) sanity | 조 빠짐/중복/**폭주(반각 과탐)** |
| 청킹 | 빈 청크, 길이 분포 | 청크 이상 |
| 색인 | 벡터 수=청크 수, 차원 1024 | 적재 누락 |

- 1..N 연속 = 도메인 불변식(약관 조는 연속). 깨지면 파싱 오염 → 그 문서 불신.
- 참고: OCR=CER/WER, 레이아웃=DocLayNet/FUNSD.

## 8. 답변 완결성 — "완벽한 답 = 조회가 아니라 조립"

소비자 질문의 답은 한 값이 아니라 **특약·보통약관·별표에 흩어진 조각을 준용·강제첨부로 해소해 조립**한 것. 지급률만 답하고 면책을 빠뜨리면 소비자가 손해 → **완결성 계약**으로 관리:

- **답변 계약(질문유형별 완결 스키마)**: "얼마?"의 완결 답 = 지급률 + 감액 + **면책** + 보장범위(별표) + 준용범위. 뭘 다 채워야 완벽한지 미리 못박음.
- **준용 폴백**: 특약에서 NULL → `parent_policy_id`로 보통약관 재조회. 없으면 "확인불가" 명시(환각 금지).
- **강제 첨부**: 담보/지급 질의엔 `coverage_exclusion_map`으로 면책을 **항상** 붙임(점수 무관).
- **완결성 게이트**: 답 내보내기 전 "필수 요소 다 찼나?" 체크 → 누락 시 보충 or 명시.
- 홉의 대부분은 **인덱스타임에 엣지로 해소됨**(clause_ref·exclusion_map·parent_policy_id) → 런타임은 값싼 순회+조립.

**구현/측정**: `scripts/assemble_answer.py`(엣지 조립기) + `data/eval/golden_completeness.jsonl`(질문→필수요소집합). 채점 = 필수요소 recall. 완결성 게이트가 처음엔 4/5로 **별표3 ICD 판정 갭을 검출** → 그 홉(`judge_coverage.py`)을 만들어 연결하니 **6/6·recall 1.00**(현재). 이것이 우리가 논의한 **멀티홉/에이전트 골든셋**의 실체 — 게이트가 "뭘 더 만들지"를 가리킨다.

**별표3 ICD 보장판정(`judge_coverage.py`, 7/7)**: 약관은 병명이 아니라 KCD 코드 범위로 보장을 정의(암=C00~C97+특정D). 판정 규칙: ①담보 특정성(C=일반암 / D00~D09=제자리암 / D37~D48=경계성 — 같은 코드도 담보 따라 갈림, D05는 암진단자금엔 미보장·제자리암엔 보장) ②제외 우선 ③3-값(보장/미보장/**판정불가**=억지 판정 안 함). 코드 모델=(문자,주,부) 튜플 구간 포함. 병명→코드는 별도 계층(판정기는 코드만).

**사실 reconciliation(`assemble_answer` --reconcile, 4/4)**: 조립이 모순 팩트를 그냥 나열하면 소비자가 오해(payout 50% + 미보장) → **보장판정이 payout을 게이팅**한다(제외 우선). 미보장이면 실제 담보로 **리다이렉트**("D05는 암진단자금 미보장 → 제자리암진단자금 10%"), 판정불가면 전문가. 이로써 "완벽한 답"은 완결(빠짐 없음)에 더해 **정합(모순 없음)** 까지.

**면책 준용 — 데이터가 설계 가정을 교정**: 처음엔 "특약 면책 없으면 보통약관 홉" 폴백을 예상했으나, 실측상 **4개 약관 모두 자기 면책 조 보유**(담보별 면책은 특약 고유 — 중환자실 면책 ≠ 치아 면책). 준용되는 건 청약철회·해지 같은 **공통 계약규정**이지 담보 면책이 아님. 단 진짜 준용 대상 = 보통약관 **공통 면책**(전쟁·임신·위험활동 등) — 라이나 특약은 부모가 corpus에 없어 **"준용 소관·미확보→확인 필요"로 플래그**(`exclusion_common_pending`, 완결성 6/6). 없는 걸 안전하다 하지 않는 게 핵심. 또 면책 조 본문의 **사유 목록**을 `extract_exclusion_reasons`(12/12)로 뽑아 exclusion을 "제목"에서 "실제 사유"로 깊게 하고, 특약이 **미기재한 표준 공통면책만** 정밀히 준용 플래그(라이나 특약: 고유=고의, 준용대상=위험활동·임신출산·전쟁내란·직업위험).

**합성(마지막 마일)**: 조립된 구조화 팩트를 `format_answer`가 소비자용 답변 한 문단으로 엮는다(결정론 템플릿 — 근거는 element별 골든이 보증). 질의 의도 파싱도 *"재해 아닌"=질병* 부정 처리 + 담보가 **안 쓰는 축은 필터 스킵**(중환자실은 cause 미분할이라 감액은 reduction 필드로). 예: "중환자실 재해 아닌 병 얼마+면책?" → *"1일당 1%(10일 한도, 1년내 재해외 50% 감액) · 면책: 고의 · 공통면책 준용 미확보 · 청약철회 준용"*.

## 9. 검색 골든셋 — recall@k (검색 ≠ 생성 분리)

앞 8개 절의 골든은 **추출·조립**(결정론, 스택 없이 자립)을 잰다. 그런데 RAG 품질 저하는 두 곳에서 온다 — **검색이 정답 청크를 못 가져왔거나(retrieval)**, 가져왔는데 **LLM이 틀리게 썼거나(generation)**. 이 둘을 섞으면(RAGAS만 보면) "왜 틀렸나"를 못 짚는다. 검색만 따로 재는 게 `eval_retrieval.py`.

**정답 정의 — 원문 verbatim 앵커(chunk_id 아님):** 각 질의의 정답 조에만 나오는 구절을 골든에 박고(`"anchor": "입원간병인 사용확인서"`), `/retrieve` top-k 중 **아무 청크 본문에 그 앵커가 있으면 hit**. chunk_id로 채점하면 재청킹·재색인 때마다 골든이 깨지지만, 원문 구절은 안 바뀐다. 매칭은 §4의 `_norm`(공백·구두점·전각 흡수)을 그대로 재사용.

| 지표 | 정의 | 무엇을 보나 |
|---|---|---|
| **recall@k** (k=1,3,5,10) | 질의당 hit@k 평균 | 정답을 top-k 안에 넣었나 (LLM 컨텍스트에 들어갔나) |
| **MRR** | 1/(첫 정답 순위) 평균 | 얼마나 **상위**에 올렸나 (리랭커 감도) |

**첫 측정(라이나 간병인 R04, 12문항)**: `recall@1=0.58 · @3=0.92 · @5=0.92 · @10=1.00 · MRR=0.75`. 전부 top-10 안엔 있으나(@10=1.0) 상위 정확도는 갈림 — **골든이 실제 검색 약점을 검출**: *"해지된 특약을 다시 살릴 수 있나요?"*(제18조 부활)가 **7위·rerank 0.075**. 구어체 "다시 살리다" vs 약관 용어 "**부활(효력회복)**"의 어휘 불일치.

**측정이 가설을 교정한 사례 (검색≠생성 분리의 실전):** distractor를 뜯어보니 실패가 세 갈래 — ①목차·요약박스가 실제 조와 경쟁 ②**청킹 heading 결함**(ODL이 조 제목을 `-` 리스트/문장꼬리 H6로 뱉어 갱신·제10조가 쓰레기 heading 상속) ③리랭커 어휘갭(부활). ②를 고치려 청커에 heading 복구 패스(`chunker_adaptive._repair_markdown_headings` — 조 제목 승격·문장꼬리 강등·점선 TOC 제거)를 넣고 재색인했으나 **recall이 안 움직임**. 원인: 리랭커가 `(query, content)`만 봤다(`search.py`). 즉 heading을 고쳐도 최종 순위(=rerank)에 안 실림. → 진짜 레버는 **리랭커 입력**이었고, 덴스 임베딩은 이미 `heading_path+content`인데 리랭커만 content-only인 불일치를 `_rerank_text`로 맞춤. **결과 `recall@1=0.83 · @3=1.00 · @5=1.00 · MRR=0.92`** (부활 7→2위, 갱신 2→1위, 연체 2→1위, 회귀 0). heading 복구는 **전제**(heading이 맞아야 리랭커에 먹임)였고, 두 수정이 맞물려 순증. 동의어 사전 없이 어휘갭(부활)까지 해소된 게 핵심 — 조 제목이 곧 도메인 어휘였다.

**순증(monotonic) 게이트**: `data/eval/retrieval_baseline.json`에 recall@k·MRR을 고정. 청킹 파라미터·프리페치 배수·리랭커를 바꾼 뒤 재측정해 recall@5·MRR이 baseline보다 떨어지면 ❌ exit 1(회귀), 유지/향상이면 ✅. baseline 갱신은 `--update-baseline`. 위 수정도 이 게이트로 순증 확인 후 baseline을 새 수치로 고정했다.

**세그먼트 분해 — 측정이 파인튜닝 가설을 반증(`eval_retrieval --segment`)**: [roadmap §1.4](roadmap.md)의 병목 판별식은 "**도메인 용어 쿼리가 일반보다 검색 열위면 retrieval-bound → 임베딩 대조학습(Phase 1)**"을 트리거로 둔다. 이를 실측하려 골든 25문항을 **도메인 어휘 vs 일반**(공개 목록 `DOMAIN_VOCAB`: 중환자실·소득보장수술·특약·갱신·해약환급금·충치… 기반, 재현 가능)으로 갈라 채점했다:

| 세그먼트 | n | recall@1 | recall@5 | MRR |
|---|---|---|---|---|
| 도메인 어휘 | 19 | **0.842** | 1.000 | **0.921** |
| 일반 | 6 | 0.500 | 1.000 | 0.672 |

가설과 **정반대** — 도메인 어휘 질의가 오히려 더 잘 검색된다. 중환자실·소득보장수술 같은 **변별력 있는 약관 용어가 강한 검색 앵커**라 정답을 rank1에 올리는 반면, 일반적 표현("입원비 보험금은 어떤 경우")은 여러 청크와 경쟁해 순위가 흐려진다. recall@5는 집계 1.0의 귀결로 두 세그먼트 모두 1.0이라 **판별 신호는 미포화 축(recall@1·MRR)**에 있다(판별식이 @5 대신 @1·MRR로 세그먼트 비교하는 이유). → **retrieval-bound를 더 견고히 배제**하고 Phase 1(도메인 임베딩) 가설을 기각 방향으로 민다. 단 일반 세그먼트 n=6은 작아 방향 신호로만 쓰고, 골든 확장·재라벨은 후속(§1.2 코퍼스 마이닝). 판정은 `make diagnose`가 `retrieval_segments.json`을 읽어 자동 반영.

**왜 `make check`에 안 넣나**: `check.py`는 **스택 없이 도는 자립 게이트**(추출·조립)라 계약이 "docker 불필요". 검색은 Qdrant·리랭커가 실제로 떠 있어야 채점되므로 넣으면 그 계약이 깨진다 → `smoke_test`·`eval_ragas`와 같은 계열의 **별도 스택 게이트**(`make eval-retrieval`). 이로써 4단계 골든이 다 채워짐:

```
파싱   parse_golden          자립  make check
추출   payout/terms/coverage… 자립  make check
검색   eval_retrieval        스택  make eval-retrieval   ← 이 절
답변   completeness/reconcile 자립  make check  +  RAGAS(스택)
```
